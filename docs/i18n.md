# Internationalization (en / vi / fi)

Macroyo ships in English, Vietnamese (`vi`) and Finnish (`fi`). The default is English.

## How the language is chosen
- Profile → Language: **System / English / Tiếng Việt / Suomi** (`AppData.language`, saved with the rest of the data).
  The welcome step of onboarding has the same picker.
- **System** (also the default for old data without the field) reads the device language list
  (`navigator.languages` on web, `Intl.DateTimeFormat().resolvedOptions().locale` on Hermes and as a fallback; no native module needed) and picks the first tag whose
  primary subtag is `vi` or `fi`; otherwise English. (`sv-FI` is Swedish, so it stays English.)
- The choice is applied on load and when it changes. On web, `<html lang>` follows it.

## Library choice (read this)
The brief asked for i18next + react-i18next + expo-localization. **Installing them was blocked by the environment's
safety review (3 attempts, not worked around)**, so `src/i18n/` is a small dependency-free layer that deliberately uses
the **same catalog format**, so switching to i18next later is a drop-in:
- flat dotted JSON catalogs (`locales/{en,vi,fi}.json`), `{{param}}` interpolation;
- plurals with `_one` / `_other` suffixes, chosen by `Intl.PluralRules` when `params.count` is a number;
- fallback: active language → English → the key itself.
`useI18n()` (React) returns `{ locale, t, tm }`; `t(key, params)` is typed against `en.json`, so a wrong key fails `tsc`.

## Domain code returns messages, not sentences
Calculation code (`nutrition`, `projection`, `offset`, `store`, …) returns `Msg = { key, params? }` (build with `msg()`).
The UI translates with `tm(message)` at render time, so changing the language re-renders correctly, and tests assert keys
or the English text via `en(message)` from `src/i18n/testing.ts` (it also shows no-break spaces as plain spaces).
Params may themselves be `Msg` values. Stable English ids that are never shown (`band`, `who`) stay plain strings.

## Adding or changing text
1. Add the key to `en.json`, then to `vi.json` and `fi.json` (tests fail until all three have the same keys and `{{placeholders}}`).
2. Plurals: add `key_one` and `key_other` in every language (vi has no plural forms: give both the same text).
3. Never hardcode text in `.tsx`: `src/i18n/noHardcodedText.test.ts` scans JSX text and text-like props.
4. Numbers and dates go through `src/lib/format.ts` / `src/lib/dates.ts`, never `toFixed` or string concatenation.
5. Units stay `kg`, `lb`, `cm`, `ft`, `in`, `kcal`, `g` and are joined to the number with `withUnit()` (U+00A0).

## Formatting (Intl)
| | en | vi | fi |
|---|---|---|---|
| number tag | en-US | vi-VN | fi-FI |
| 1234.5 | 1,234.5 | 1.234,5 | 1 234,5 (U+00A0/U+202F group) |
| percent | 52% | 52% | 52 % (no-break space) |
| date tag | en-GB | vi-VN | fi-FI |
| long date | Wednesday 28 October | Thứ Tư, 28 tháng 10 | keskiviikko 28. lokakuuta |
| short date | 28 Oct | 28 thg 10 | 28.10. |
| week strip | M T W T F S S | T2 T3 T4 T5 T6 T7 CN | M T K T P L S |

- Negatives use the real minus sign U+2212 ("−300"), never a hyphen.
- Week-strip letters are catalog keys (`date.narrow.0` = Sunday), not Intl `narrow`, so devices can't disagree.
- Values are rounded half-up first, then formatted; no grouping inside input boxes ("1234,5").

## Parsing typed numbers (`parseDecimal(raw, locale)`)
- **Both "." and "," are accepted as the decimal mark in every language** (phone keyboards often differ from the UI language).
  "80,5" and "80.5" both mean 80.5.
- **The earlier "1,234" safety decision stays**: text such as "1,234" (one separator followed by exactly three digits) is
  ambiguous (1.234 or 1234?) and is **rejected in every language** with the "thousands separator" message, because a
  weight of 1.234 kg or a calorie target of 1234 would be a silent mistake.
  In **Vietnamese** "1.234" is also rejected (there "." is the thousands mark). In en/fi "1.234" is a plain decimal.
- **Finnish** thousands groups written with a space ("2 500", "2 500,5", also U+00A0/U+202F) are accepted when the groups are
  exactly three digits ("2 50" and "80 5" are rejected).
- Round trip: whatever an input box shows (`formatInputNumber`) parses back to the same number in its language.
- Hints and error messages show the locale's decimal mark.

## Fonts and layout (from the vi/fi layout review)
- Vietnamese uses taller line heights for title 40, section 29, bodyMedium 26, secondary 22, macroGrams 22, caption 18
  (`typographyFor('vi')`), because stacked tone marks are clipped by Android's fixed line box. Sizes are unchanged.
- DM Mono (`inputNumber`) is for **digits and ASCII units only** (it has no Vietnamese letters or ₫).
- Tab labels do not scale with the system font size.
- **Label shrinking is native-only.** Segmented and Chip labels (`AppText fit`) stay on one line and shrink to 80% on iOS and
  Android (`adjustsFontSizeToFit`, `minimumFontScale 0.8`). react-native-web does not implement either prop, so on **web** the
  same labels may wrap to **two lines** instead (`fitTextProps` in `src/lib/fitLabel.ts`; the controls grow, nothing is
  clipped or ellipsized). When checking a long translation, look at the 2-line wrap on web and the 80% shrink on a device;
  `fit.py` measures the web build, so its "2 lines" WARNs are this fallback, not a bug.
- A save that is blocked by invalid input scrolls to the first invalid field (log quick-add and edit, onboarding body and plan
  steps; `useFormScroll`). Calc has no such case: its Save button is disabled while an entry is invalid and a notice explains why.
- Finnish: soft hyphens in the longest compounds, Android hyphenation on for Finnish text.
- Food names, serving labels and USDA categories are English by design (the Profile screen says so); only the sentences around them are translated.
